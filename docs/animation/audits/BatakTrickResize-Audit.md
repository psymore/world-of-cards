**Feature Name:** Batak trick-center card resize — shrink trick-center cards (in flight and resting) from in-hand ("normal") size to a smaller, constant trick footprint, instead of holding them at full size for the entire flight.

**Objective:** Replace the previous workaround — `TrickCenter`'s traveling card frozen at `size="normal"` for its whole flight because `PlayingCard`'s `"small"`/`"normal"` variants aren't uniform scales of one another (Constitution §8 gap 2) — with a mechanism that actually shrinks the card, coordinated with its own travel, without reproducing the landing-moment "pop" that mismatch originally caused.

**Constitution References:** §5.I (Layered Ownership), §5.II (SSOT), §5.III (Explicit Contracts — the size-variant non-linearity itself), §5.V (Visual State Continuity — the local-departure→`TravelCard` scale handoff, see Risks below), §5.VI (Coordinated Property Timelines — the primary principle this work is exercising), §5.IV (trivial, see Layer 2 row below), §8 gap 2 (this change is a direct attempt at a working reference implementation for the gap that principle names).

## Risks

- **§5.V — Visual State Continuity (the local-departure→`TravelCard` scale handoff):** this diff creates a scale handoff across a component boundary. `BatakHandCard.tsx:211-216` animates `scale` toward `LOCAL_DEPARTURE_SCALE` over the local-departure leg; `BatakHandCard` then unmounts and `TrickCenter.tsx:141-142` mounts a fresh `TravelCard` at a **hard-coded** `originScale={TRICK_CARD_SCALE}` — not a value read from `BatakHandCard`'s actual final animated state. §5.V's rule ("a transition's initial value must be read from the property's true current state... never from a recomputed or reset baseline") is normally about reading a *live* value at handoff time; here there is no live read at all — the new phase's starting value is a second, independently-declared constant that happens to be defined as literally the same number (`trickCardScale.ts:13`: `export const LOCAL_DEPARTURE_SCALE = TRICK_CARD_SCALE;`) and consumed by both sides via that same import, not by measurement.
  - **Why this is arguably compliant by construction, not in spite of §5.V:** §5.V's underlying concern is a stale/wrong starting value causing a visible pop (its own evidence, the `useCardMotion` jump bug, was exactly a value that was never actually true at the moment it was used). Here there is no possibility of the two sides drifting at *edit* time — `LOCAL_DEPARTURE_SCALE` is defined as an alias of `TRICK_CARD_SCALE`, not an independently-tuned sibling constant (contrast with `TRICK_CARD_CONTENT_SCALE`, which *is* independently tuned) — so §5.II (SSOT) is what's actually doing the work of keeping these two numbers equal, not a live read. This is a legitimate alternative to §5.V's literal mechanism (bind the start value from a live read) precisely because the "previous phase's actual final value" and "the next phase's declared starting value" are constitutionally guaranteed identical by definition, not by coincidence.
  - **Where this could still fail, and why it isn't purely a numbers question:** the guarantee above only covers the *scale* value itself. It does **not**, on its own, cover *timing* — whether `BatakHandCard`'s local-departure `withTiming` animation has actually visually reached `LOCAL_DEPARTURE_SCALE` by the moment `BatakScreen.tsx`'s departure timeout unmounts it and `TrickCenter` mounts `TravelCard` in its place. Checked directly: `HumanHandFan.tsx:160` passes `localDepartureDurationMs={LOCAL_DEPARTURE_DURATION_MS}` into `BatakHandCard` (used as the `withTiming` duration, `BatakHandCard.tsx:215`), and `BatakScreen.tsx:363` fires its own handoff `setTimeout` after that *same* `LOCAL_DEPARTURE_DURATION_MS` constant — so this isn't two independently-chosen values either, it's the same SSOT pattern as the scale constants. The residual risk is narrower than "the two durations disagree": it's whether a JS-thread `setTimeout` (subject to JS-thread scheduling jitter) reliably fires at the same wall-clock moment a UI-thread Reanimated `withTiming` animation of the *same nominal duration* actually completes — the two run on different threads under this codebase's Reanimated-based execution model (Project Decisions §7 item 1, superseded for `apps/mobile` by `ADR-002`), so "same duration value" doesn't guarantee "same completion frame." Not reproduced by code read alone — flagged for the on-device pass (Task 7 Step 4's "does the shrink during local departure look smooth or abrupt" question already covers this symptom, even though it wasn't previously connected to this specific mechanism).
- **§5.VI — Coordinated Property Timelines (the two cases the task brief flagged for genuine scrutiny):**
  - `BatakHandCard`'s local-departure effect: before this diff, its `motion.setTarget({ x, y, timing })` call already coordinated two properties atomically (`useBatakCardMotion.setTarget` applies the same `duration`/`easing` to every field present in one call, all launched together — see `useBatakCardMotion.ts`). This diff adds `scale` to that same call, at the same call site, using a field (`BatakCardTarget.scale`) that already existed and was already used by this exact file's selection-lift and deal-entrance effects. This is populating an already-coordinated field with a real value, not building new coordination — the mechanism (one `setTarget` call = one atomic retarget) is unchanged.
  - `TrickCenter`'s `TravelCard` usage: `TravelCard.tsx`'s `originScale`/`restScale` props were already wired into the same single `progress` Animated.Value driving `translateX`/`translateY` (defaulting to `1`/`1`, a no-op, before this diff — see the component's own doc comment: "translateX/translateY/rotate/scale all share the one `progress` value, so they're guaranteed frame-perfect in sync"). `TrickCenter` now supplies real values instead of the no-op default. Same conclusion: activating pre-existing coordination, not adding new coordination machinery.
  - Conclusion for both: **no §5.VI violation, and no new coordination mechanism introduced.** This is the primary finding this audit was asked to make a real call on, not just check as an eligibility box.
- **`LOCAL_DEPARTURE_SCALE`/`TravelCard` split** — already covered under Severity above; the open design question is *where* the shrink happens in the timeline, not *whether* it's coordinated.
- **Reduced motion:** `BatakHandCard`'s local-departure effect returns early under `reducedMotion` (`if (!isDeparting || departed.current || reducedMotion) return;`), same as before this diff — under reduced motion the departure leg's `scale` change (like its `x`/`y`) simply never fires, and `TravelCard`'s own `reducedMotion` path snaps `progress` to `1` immediately (landing at `restScale` with no animation). Net visual result is correct (card ends at the shrunk size with no animation, matching this codebase's established "skip flourish, arrive instantly" reduced-motion convention), but this diff didn't add or change that branching — flagged for completeness, not as a new risk.
- **`GatherCard`'s constant `TRICK_CARD_SCALE` interacts with a non-center `transformOrigin` — real risk, not "correct by construction."** An earlier draft of this audit asserted this was safe by construction; that was wrong and has been corrected. `GatherCard.tsx:117-143` places `{ scale: TRICK_CARD_SCALE }` inside the *same* `useAnimatedStyle` objects (`frontStyle`/`backStyle`) that also set `transformOrigin` from `resolveFlipGeometry` (`GatherCard.tsx:55-70`) — `'50% 100%'` for a bottom-bound flip, `'50% 0%'` for top, `'100% 50%'` for right, `'0% 50%'` for left, never the default center origin `TrickCenter`'s resting cards implicitly scale around. A uniform `scale` about an off-center origin does not shrink content in place — it displaces the visual center toward the origin point. At `TRICK_CARD_SCALE = 0.75` and `CARD_DIMS.normal = { width: 94, height: 132 }`, the displacement is approximately `(1 − 0.75) / 2 × 132 ≈ 16px` vertically for top/bottom-flipping seats and `(1 − 0.75) / 2 × 94 ≈ 12px` horizontally for left/right-flipping seats. **This displacement did not exist before Task 6's diff** — the pre-diff `frontStyle`/`backStyle` transform arrays had no `scale` entry at all, only `perspective` and the flip rotation. Not fixed in this pass (this is a Risk to name accurately, the code is not being changed here) — explicitly added to the Task 7 Step 4 on-device checklist below: does the gathered card visibly jump sideways/vertically at the exact instant the flip starts, for each of the four seat directions?
- **Re-activating `TravelCard`'s scale interpolation has direct prior history in this exact codebase.** `originScale`/`restScale` were not generic, never-used scaffolding — they were built specifically for `TrickCenter`'s human-play call site (2026-07-21 design work), used with `SELECTED_SCALE`/`NORMAL_TO_SMALL_SCALE`, and then explicitly reverted in `d954399` for producing a visible pop, because that interpolation crossed the non-linear `"small"`/`"normal"` boundary. This diff's AI-play re-activation (`originScale={1}`, `restScale={TRICK_CARD_SCALE}`, `TrickCenter.tsx:160-161`) is materially different — both ends of the interpolation are the same `size="normal"` card, so it never crosses that non-linear boundary — but it is still the same *category* of thing (interpolating a card's scale across a flight) that already produced a visible defect once in this codebase. That prior failure is directly relevant context for the user's on-device pass, not just historical trivia — flagged explicitly rather than left implicit.
- **Tuning basis:** `TRICK_CARD_SCALE`/`TRICK_CARD_CONTENT_SCALE` were tuned live against real `PlayingCard`s via the playground's Demo10 tool (per `trickCardScale.ts`'s own doc comment), not verified by an automated test — consistent with the standing 2026-07-07 no-new-tests policy and Constitution §5.VIII's still-conditional status.

## Open Questions

- Does this diff's approach (stay at `size="normal"`, compensate via an outer `scale` + `contentScale`, never switch size variants) constitute a working reference implementation for Constitution §8 gap 2 ("§5.VI has no working reference implementation for property pairs whose end-states are not linearly related")? It resolves the *symptom* (no more landing-moment pop from variant-switching) without resolving the *underlying* non-linearity between `"small"` and `"normal"`. Not resolved here — updating §8 gap 2's status is a Constitution §10 action, out of scope for this audit, and should be raised separately if the on-device pass confirms this reads as fully resolved.
- Should `LOCAL_DEPARTURE_SCALE` be retuned to spread more of the shrink into `TravelCard`'s flight leg, per `trickCardScale.ts`'s own flagged uncertainty? Deferred to Task 7 Step 4 (on-device, the user's own pass).
- ~~Is `GatherCard`'s `scale`/`transformOrigin` displacement (Risks and Severity Classification above, ~16px/~12px estimated) actually perceptible on-device?~~ **Closed by code change, not by measurement:** the final whole-plan review pass moved `scale` to the center-origin group layer rather than waiting to find out whether the displacement was perceptible. The on-device check remains, downgraded to confirming the fix.
- Does the `contentScale` discontinuity at the local-departure→`TravelCard` handoff read as a visible "glyph size" pop? `BatakHandCard` renders its departing card without `contentScale`, so the corner-index/watermark compensation switches on abruptly at handoff while the card body's own scale stays continuous — the same defect class this feature exists to remove, but on the `contentScale` channel rather than `scale`. Deliberately not fixed in the review pass: the obvious remedy (push `contentScale` down into `BatakHandCard`) just relocates the jump to departure-start, and a genuinely continuous version needs a fifth shared value threaded through `useBatakCardMotion` across a component boundary.
- Both `BatakHandCard`'s local-departure `withTiming` duration and `BatakScreen.tsx`'s handoff `setTimeout` read the same `LOCAL_DEPARTURE_DURATION_MS` constant (confirmed by code read), but they run on different threads (JS-thread timer vs. UI-thread Reanimated animation) — does that cross-thread gap ever produce a visible mid-shrink jump at handoff (the §5.V timing risk in Risks above)? Not verifiable by code read alone.
- On-device verification (Task 7 Step 4) has not yet happened — this audit's Approval below is conditional on it, not a substitute for it, mirroring how `BatakHandFan-Demo08Migration-Audit.md` handled the same situation.
